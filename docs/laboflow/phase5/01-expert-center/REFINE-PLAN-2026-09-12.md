### 图8（expert-7）概念图：Skill、专家、专家团的关系与选择
- **组成关系**：`Skill（工具能力，让AI能做某件事，如[合同审查][SEO分析][内容工厂]）+ 领域经验 + 专业提示词 = 专家（AI顾问，懂某个领域的AI角色）`；`多位专家 + SOP编排（谁先做、谁后做、怎么配合）= 专家团（AI协作团队：**自动拆解、并行执行、完整交付**）`。
- **怎么选**：需要工具能力 → 装 Skill；**明确的单点问题 → 找专家**；**任务复杂、需要多角色配合 → 召唤专家团**（示例："召唤SEO内容营销团队 → **7人并行**，从关键词到转化报告全搞定"）。
- 底部总结：**Skill 是能力 → 专家是能力+经验 → 专家团是多位专家+协作流程**。

### 1.9 图文合计的关键结论
1. 召唤 = 详情卡 CTA 或「+」菜单选择器（带搜索、当前选中勾选、"召唤更多专家"入口）；召唤后**会话级绑定**该专家/团队，专家可持续对话、可换模型。
2. Workbuddy 的 `@` = 引用对话文件，`/` = 技能与指令；**它不用 @ 召唤专家**。我们按用户要求扩展 @ 语义，属差异化设计。
3. 专家团确有**主持人**（⭐徽标）；能力介绍即分工协议（SOP）；支持**快速模式**（小需求轻流程）。
4. 团队执行是**单会话 + 主持人编排 + 成员状态条 + 主持人 @成员 叙述**；"专家互相对话的群聊"在产品呈现上并不存在——呈现的是主持人的调度叙述，执行层是各成员独立干活。
5. 交付标配：产物文件卡、所有产物/变更聚合、消耗显示、**用户下一步建议**。
6. 概念公式：专家 = Skill + 领域经验；专家团 = 多位专家 + SOP 编排（自动拆解/并行执行/完整交付）。

## 2. LaboFlow 现状与差距

已有（此前模块 01 已落地）：
- `matchExpertMention`（app-store.ts:4761）：`^@(\S+)\s*(…)$` 解析启用的专家名 → `api.invokeExpert({sessionId, expertId, task})`；未知名不劫持、回落普通消息；60s TTL 缓存。
- Composer「+」菜单 → 选择专家 → 插入 `@专家名 `（与 @ 拦截共用一条管线）。

- 设置 → Agent → 专家（专家/专家团编辑器，真实模型/技能选择器）。

差距（对应三点需求）：

| # | 差距 | 现状 | 目标 |

## 3. Q1 方案：@ 召唤专家（与专家团）

### 3.1 设计
- **语义扩展**：`@` 弹层在「会话」「文件」之上新增「**专家**」组（含专家团，混排同 Workbuddy 图5）；选中后插入既有 token `@名字 `，**复用现有 sendPrompt 拦截管线**，不新发明调度语义。
- **顺序**：专家组置顶（召唤是 @ 的首要新意图），其后 会话、文件 —— 与"专家名优先拦截"的发送语义一致。（可选：维持 会话 在前；默认方案按专家置顶实现，批准时可改。）
- **来源**：`api.listExperts()` + `api.listTeams()`（IPC `expertList`/`expertTeamsList` 均已存在，**零新增 IPC**）；仅列 `enabled !== false`；TTL 缓存并入现有模块级缓存模式（`SOURCE_TTL_MS` 10s，与 commands/files 同 key 规则）。
- **过滤**：名称/描述/标签 模糊匹配（复用 `fuzzyMatchPath` 的评分风格或 `compareMatches`），上限 `MAX_EXPERT_ITEMS = 8`（对齐 `MAX_CONTEXT_ITEMS`）；空 query 显示全部（最近/预设优先）。
- **弹层渲染**：`AutocompleteItem` 联合类型增 `{ kind: "expert"; expert; match }` 与 `{ kind: "team"; team; match }`；`ComposerAutocomplete` 复用**现有分组头机制**（lastGroup 逻辑，`"expert"` 组头「专家」），行样式：IconGraduationCap（专家）/IconUsers（团队）+ 名称 + 来源徽标（预设/自建）+ 一行简介截断；键盘上下/回车/Esc/IME 冻结全部复用现有状态机。
- **accept 行为**：专家 → `applyCompletion(value, trigger, "@名字 ")`；团队 → `@团队名 `。发送侧：
  - `matchExpertMention` 扩展为先解析专家、再解析团队（同缓存模式，第二个 map）；团队命中 → `api.invokeExpertTeam({sessionId, teamId, task})`。
  - 保持"未知名不劫持"回落语义不变。

### 3.2 触碰的文件（授权点见 §6 A1–A4）
- `apps/desktop/src/hooks/use-composer-autocomplete.ts`（PI-Desktop 原始文件，含你未提交的会话引用改动）：联合类型、来源合并（~10 行）、accept 分支（~12 行）。
- `apps/desktop/src/components/ComposerAutocomplete.tsx`（同上状态）：行渲染 + 组头（~30 行）。
- `apps/desktop/src/stores/app-store.ts`（我方 T51.5 既有改动）：matchExpertMention 团队解析（~20 行）。
- `apps/desktop/src/components/Composer.tsx`：+菜单与 @ 一致化（团队项，可选）。
- i18n：8 locale 各 3–4 个键（组头「专家」「专家团」、行徽标）。

### 3.3 验收标准
- A-1 输入 `@` 即弹层出现「专家」组（启用中的专家与专家团），名称/描述/标签模糊过滤可用，上限 8 条。
- A-2 选中专家插入 `@专家名 `；选中团队插入 `@团队名 `；键盘/Esc/IME 行为与现有弹层一致（不新增快捷键语义）。
- A-3 发送 `@专家名 任务` → 专家被调度、来源会话收到完成卡（现有行为回归不变）；发送 `@团队名 任务` → 团队 run 启动并回帖 team-card。
- A-4 未知名（非专家非团队）`@foo` 消息照常发给 agent，不被劫持（既有用例回归）。
- A-5 「+」菜单选择专家仍工作（同一管线回归）。

## 4. Q2 方案：Prompt + 上下文传递

### 4.1 语义（对齐 Workbuddy："专家只处理用户提供的对话内容和文件"）
**只传用户显式提供的上下文，不自动携带当前会话历史**（成本与意图清晰性；自动携带列为 P2 可选项，需用户点头再做）。显式上下文两类：
1. **附件文件**（composer 附件 chips，`draft.fileReferences`）→ 在 envelope 中列 `[文件]` 路径清单；专家与主应用共享工作区 cwd，**由专家用工具自行读取**（不内联内容，避免 prompt 膨胀）；工作区外绝对路径同样列出（驱动侧有 fs 能力边界时自然受限，卡片中可见）。
2. **引用会话**（你未提交的会话引用特性，`attachSessionContext` → `composerAttachSession` 管线）：对专家派发场景，P0 取**引用会话的摘录**（最近 N 条消息、字符上限 ~8k，超限截断并注明"已截断"）内联进 envelope。

### 4.2 Envelope 格式（渲染侧拼装，主进程 P0 零改动）
```
<用户任务原文>

[上下文]
- 文件：path1、path2（可在工作区直接读取）
- 引用会话「<标题>」（近 N 条）：
  <user> …
  <assistant> …
  （已截断）
```
- 拼装点：`sendPrompt` 拦截分支内，用 `draft` 构建 envelope 后作为 `task` 传 `api.invokeExpert` / `invokeExpertTeam`。**expert-service/team-runner 无需改**（task 本就是自由文本；会话标题仍取前 24 字，不受影响）。
- P2（可选，另批）：`ExpertInvocation` 增结构化 `attachments`/`contextRefs` 字段，卡片与标题更精准。

### 4.3 验收标准
- B-1 带附件 @专家：专家会话首条 prompt 含 `[上下文]` 段与附件路径清单；专家完成卡正常回帖。
- B-2 带引用会话 @专家：prompt 含引用会话摘录，超 8k 字符被截断且注明。
- B-3 无附件无引用：prompt 与现状完全一致（裸任务文本，回归）。
- B-4 普通消息（无 @）附件/引用会话行为不变（现有管线回归）。
- B-5 单测：envelope 构建函数（附件/引用/截断/空四例）；matchExpertMention 团队解析。

## 5. Q3 建议：专家团执行模式（完整建议书）

### 5.1 结论
**保留并强化现有「Loop pipeline（pi-agent-loop 协议）+ 星型 DAG 独立专家会话」作为专家团执行模式；不采用"主持人拉群聊、专家互相对话"模式。** 同时吸收 Workbuddy 的**呈现层**优点（成员状态条、主持人调度叙述、下一步建议、快速模式）——这些是"看起来像群聊"的关键，而其执行层本就是主持人编排各成员独立执行（图7 证据）。

### 5.2 理由（为什么不做群聊）
1. **架构侵入**：Pi-Desktop/agent-runtime 没有多方共享会话原语。真群聊需要新的多租户会话内核（共享上下文、多方发言路由、发言权调度）——这是对核心的大幅侵入，直接违反最小侵入原则。
2. **概念裁定**：R5 已裁定 专家=独立 Agent（独立持久会话）。群聊把多个 persona 塞进同一上下文，破坏该裁定；我们的 pipeline 每阶段只有一个专家上下文在线，与裁定一致。
3. **成本与收敛**：Workbuddy 自认团队成本 3–5x；群聊每轮全上下文重放，消息量 O(n²) 膨胀，且收敛不可控（客套循环/观点漂移）。Loop 协议用 `[LOOP:DONE]` 显式裁决 + maxRounds 硬顶（打满不收敛=失败，绝不静默交付），确定性可验收；预算 80% 警告/100% 停止已实现。
4. **协议正统**：pi-agent-loop（goal/pipeline/loop_control）是 Pi 官方包语义，我们已按其协议落地（调研文档 06-loop-orchestration-research.md），继续沿用=不造轮子；Workbuddy 文档亦无 loop-workflow 之类的官方多体会话机制。

### 5.3 目标架构（执行层已落地，本次补"传达层/呈现层"）
```
用户 @团队名 任务
  └─ invokeExpertTeam(sessionId, teamId, task)
       └─ TeamRunner
           ├─ [pipeline 模式] 阶段 s1→s2→…（stageExperts 指定专家）
           │    每阶段: 独立专家会话 round 循环（上轮输出回灌）
           │    退出: 专家输出含 [LOOP:DONE] 或 maxRounds 打满→run=failed
           │    阶段摘要作为下一阶段输入；阶段帧广播 {stage:{index,total,name,round,maxRounds,expert}}
           ├─ [非 pipeline] 主持人一次性 JSON 拆解 → DAG 拓扑并行(≤4) → 集成
           ├─ 预算 80% 警告 / 100% 停止；成员失败可重试
           └─ 会话回帖 team-card（kind 持久化）
```
