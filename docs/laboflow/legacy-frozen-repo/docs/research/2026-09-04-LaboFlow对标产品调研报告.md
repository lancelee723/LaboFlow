## 一、Pi Agent（earendil-works/pi）—— LaboFlow 选定的核心引擎

### 1.1 身份与现状
- 定位："minimal agent harness"，口号 "Adapt Pi to your workflows, not the other way around"；既是终端 coding agent，也是一组可复用库（统一 LLM API、agent loop、终端 UI），**官方支持基于它构建自己的产品**。
- 原作者 Mario Zechner（badlogic，libGDX 作者）；2026 年 4 月出售给 Earendil Works（Armin Ronacher 等创立），repo 迁至 github.com/earendil-works/pi，npm scope 变为 `@earendil-works/`。
- 核心 **MIT**（承诺永久），规划 Fair Source + 专有企业层的商业模式；名称/logo 归 Earendil 商标。
- 活跃度：**约 102k stars**，最新 commit 2026-09-03（调研前一天），最新 release v0.84.4（2026-08-28），**约每周一个 minor，breaking changes 常见**。
- 注意：新外部贡献者的 issue/PR 默认自动关闭，上游修 bug 不可按常规开源项目预期——需有锁版本/自维护准备。

### 1.2 架构（TypeScript monorepo，无 Rust）
| 包 | 作用 |
|---|---|
| `pi-ai` | 统一多 provider LLM API，自动模型发现 |
| `pi-agent-core` | agent 核心循环、tool calling、状态管理、transport 抽象 |
| `pi-tui` | 差分渲染终端 UI 库（可独立使用，LaboFlow 不需要） |
| `pi-coding-agent` | CLI/TUI 组装层，**SDK 也在这个包里** |
| `session-backends/sqlite-node` | SQLite 会话后端 |
| `protocol/client/server`、`chord` | RPC 协议与 client/server 分离架构（公开文档少） |

- Agent loop：经典消息→流式响应→tool calls→回喂循环；支持流中打断（steer）、排队追问（followUp）、自动 compaction、thinking level（off~max）、**会话中途切换模型/provider**。
- 内置工具 8 个（read/bash/powershell/edit/write/grep/find/ls），默认启用 4 个；`edit` 返回标准 unified patch。
- 会话：JSONL 文件、**树状结构支持单文件内分支**（/tree、/fork、/clone）；`SessionManager` 提供 `inMemory()`、`open()`、完整 tree API，SQLite 后端可用于自建持久层。

### 1.3 扩展机制（对 LaboFlow 最关键）
- **Extensions**：TypeScript 模块，jiti 加载无需编译；`registerTool`（LLM 可调用的自定义工具）、`registerCommand`、`registerProvider`（动态注册模型供应商）、覆盖内置工具；事件钩子极细：**`tool_call`（执行前，可改写参数、可 `{block: true}` 阻断——实现权限审批的抓手）**、`tool_result`（执行后改结果）、`before_agent_start`（改 system prompt）、`context`（改 messages）、provider 请求级钩子等。
- **Skills**：完整实现 Agent Skills 开放标准（SKILL.md，YAML frontmatter name/description/license 等，progressive disclosure）——**与 Claude skills 生态天然兼容**；支持复用 `~/.claude/skills`。
- **AGENTS.md**：一级公民支持（含 per-directory、override、虚拟注入）。
- **刻意不内置**（哲学决定）：MCP、subagents、plan mode、权限审批、后台 bash、cron——全部靠 extension 自建或用生态包（pi.dev/packages 已有 5,363 个包：pi-subagents、pi-background-tasks、pi-mcp-adapter 等）。
- **分发**：`pi install npm:.../git:...`，package.json 声明 `pi.extensions`/`pi.skills`。

### 1.4 模型接入（BYOM 能力强）
- 内置 15-20+ provider：订阅制（ChatGPT/Claude Pro/Copilot/Grok/OpenRouter）+ API key 制（Anthropic、OpenAI、**DeepSeek**、Gemini/Vertex、Bedrock、Azure、Groq、Together、OpenRouter、**Kimi、Qwen、ZAI（智谱）、MiniMax**、xAI 等）。
- 自定义 provider：`models.json`（baseUrl + 四种 API 类型：openai-completions / openai-responses / anthropic-messages / google-generative-ai），支持 Ollama/vLLM/各类代理；模型级 contextWindow/cost/thinkingLevelMap 可配。
- API key 支持 `!command`（1Password/Keychain）、`$VAR` 解析；extension 可 `registerProvider` 动态注册。

### 1.5 嵌入方案（LaboFlow 客户端的关键路径）
四种运行模式：TUI / print / **RPC 模式（JSONL over stdio，专为嵌入 IDE/自定义 UI 设计）** / **Node SDK（`@earendil-works/pi-coding-agent` 内含）**。
- SDK：`createAgentSession({sessionManager, modelRuntime, tools, customTools})`；可注入自定义 ResourceLoader、inline extension、虚拟 AGENTS.md、InMemoryCredentialStore；官方用例明确包含"构建自定义 web/桌面 UI""把 agent 集成进现有应用""生成 sub-agent 的自定义工具"。
- RPC：prompt/steer/abort/set_model/set_thinking_level/get_session_stats(tokens/成本)/get_entries 等命令 + 流式事件；extension 的交互对话框可被宿主 UI 代理（`extension_ui_request/response`）。
- **无 HTTP/WS 服务端 API**（RPC 是子进程 stdio）；无多租户/鉴权概念——服务化要自建。
- **先例：Proma（Electron）已成功内嵌 Pi runtime（`adapters/pi-agent-adapter.ts`），OpenClaw 亦基于 Pi 组件构建大型产品——路线已验证。**

### 1.6 对 LaboFlow 的风险清单
1. **无权限/审批系统**：需用 extension `tool_call` 钩子自建（技术可行，官方无支持承诺）。
2. **无原生 MCP**：需自研或维护 pi-mcp-adapter 类适配层。
3. **版本节奏激进**（周更 minor、breaking changes 常见）+ 治理不确定（Earendil 收购后 Fair Source 分层）：必须锁版本、抽象防腐层、做好 fork 预案。
4. 单用户单机假设（sessions/auth/trust 均本地）：团队共享、服务端集中存储需自建。
5. 无 HTTP API：服务端执行 agent 需自己包 Node 常驻服务。

## 二、OpenAI Codex（2026-09 现状）

### 2.1 产品家族与架构
- 家族：CLI（Rust 重写，Apache-2.0，约 121k stars）、IDE 扩展（webview UI + 捆绑 Rust 后端子进程）、Web（chatgpt.com/codex）、Cloud、**桌面 App（2026-09-01 发布，macOS，"command center for agents" 定位）**。
- **"one kernel, multiple shells"**：本地同步执行（CLI/IDE）+ 云端异步执行（隔离容器）共享同一内核；桌面 App 复用 CLI/IDE 的会话与配置。
- **app-server 模式**：随 CLI 捆绑的 JSON-RPC 2.0 over stdio 服务，暴露 auth、history、approvals、sandboxing、流式事件——官方定位就是给 GUI 客户端用（桌面 App 即基于此）；另有 TypeScript SDK（spawn 进程 + stdio JSONL）。

### 2.2 Harness 特性
- **审批模型（两层解耦，值得照抄思想）**：Sandbox mode（能力上限：read-only / workspace-write / danger-full-access）× Approval policy（询问时机：untrusted / on-request / never），支持按类别（sandbox approvals、MCP prompts、skill approvals）细粒度配置；**auto-review**：审批请求先由 reviewer agent 审查（数据外传/凭证探测/破坏性操作检测），fail-closed。
- 沙箱：macOS Seatbelt、Linux bubblewrap+seccomp/Landlock、Windows 原生沙箱或 WSL2；网络默认关闭、allowlist 代理。
- **Skills：支持 Claude 风格 SKILL.md**；桌面 App 内置 skills 可视化创建/管理界面；官方 skills library 含 PDF/电子表格/docx 创建（对咨询场景现成可用）。
- MCP 完整支持（client + server 皆可）；Plugins 构建在 MCP 之上。
- AGENTS.md 生态事实标准；Git worktree 原生支持；Cloud 支持 scheduled tasks + 事件触发；桌面 App 的 **Automations 结果统一进 review queue**。
- BYOM：config.toml `[model_providers]` 自定义 base_url/wire API（Ollama/LM Studio/OpenRouter/DeepSeek 均可）。

### 2.3 UI/UX
- 桌面 App 是"多 agent 指挥中心"：threads 按 project 分组、并行监督、thread 内看 diff 并直接评论、定时任务产出进审阅队列。
- 教训（LaboFlow 要避免）：① 自定义 slash commands 强制并入 skills 引发多次回归与社区反弹；② 产品面碎片化（CLI/Web/IDE/桌面多入口+文档域名迁移）造成认知混乱；③ 首发仅 Apple Silicon 的平台限制。

## 三、ZCode（基于第一手运行经验）

ZCode 是 LaboFlow 需求的直接蓝本（用户的权限四模式描述即来自 ZCode）。作为运行于其中的 agent，以下是其实际机制的内部视角：

- **权限四模式**：①变更前确认（每步改文件/执行命令前询问）②自动编辑（自动改文件，危险命令仍确认）③计划模式（先出计划、ExitPlanMode 获批后按计划执行）④完全访问（尽量不打扰）。模式在会话级切换，与 UI 深度集成（内联审批卡、计划审批面板）。
- **Skills**：progressive disclosure（启动只注入 name/description，命中任务才加载全文）；技能可通过插件市场安装（superpowers、document-skills:pptx/xlsx/docx/pdf、skill-creator 等）。
- **MCP**：`mcp__server__tool` 命名空间自动注入；支持 stdio/HTTP；有完整的诊断技能（diagnosing-mcp/hooks/plugins/skills/commands）覆盖故障排查。
- **插件与市场**：支持多个 marketplace（zcode-plugins-official、claude-plugins-official——**直接兼容 Claude 官方插件市场**），插件可含 skills/commands/hooks/agents/MCP；有插件缓存目录与启停管理。
- **子 Agent**：Agent 工具派发 subagent（general-purpose/Explore/judge 等类型，各自工具集不同），支持后台运行（run_in_background）与完成任务后通知。
- **定时任务**：CronCreate/CronList/CronUpdate/CronDelete——cron 表达式或相对延迟，**持久化在 workspace、跨重启存活**；finite/infinite、intervalUnit 抽象。
- **Browser Use / Computer Use**：browser-use 技能（Node REPL 驱动浏览器）+ computer-use 技能（accessibility 优先、像素回退；macOS TCC 权限感知、Windows 差异处理）；设置中有对应授权页。
- **其他**：TodoWrite 任务清单渲染、EnterPlanMode/ExitPlanMode 计划门、AskUserQuestion 结构化提问、ReadSessionContext 跨会话上下文、会话摘要与上下文压缩。

**对 LaboFlow 的意义**：权限四模式、插件市场兼容 Claude 生态、定时任务持久化、Browser/Computer Use 的 OS 差异授权——都有成熟参照，语义可直接沿用。

## 四、FreeBuddy 与 Proma

### 4.1 FreeBuddy（github.com/maojindao55/freebuddy，MIT）
- 定位：**本地 CLI coding agent 的桌面工作台**（"desktop chat workspace for local CLI agents"），包装 Codex/ClaudeCode/OpenCode/Kimi/CodeBuddy 等。
- 技术栈：**Electron 43 + React 19 + Vite + TS + antd 6 + zustand + i18next 双语 + better-sqlite3**；monorepo（agent-runtime、delegation-core、workflow-core、protocol、storage-sqlite 等独立成包）。
- 引擎策略：**不自研 harness**——ACP（Agent Client Protocol）包装 Codex/ClaudeCode + node-pty 兜底任意 CLI；MCP 用官方 `@modelcontextprotocol/sdk`。
- 亮点功能：Normal Mode（多 agent 卡片并行）+ **Team Execution Mode（团队模板编排：实现+审查+测试）**；Codex 用量卡片（实时用量+限额重置倒计时+账号热切换）；Runtime Pack 签名/校验/分发；分发矩阵 dmg/brew/exe/deb/AppImage + electron-updater。
- UI：三栏（272px 侧栏/会话区/右栏笔记文件）；浅色 #f8fafc/深色 #0b0f19，teal #10b981 强调色；Outfit 标题 + Plus Jakarta Sans + JetBrains Mono；圆角 6-16px、4/8/12/16/24 间距体系。
- 缺失（LaboFlow 差异化空间）：无账号/团队/服务端/市场/定时任务/Web 管理台。

### 4.2 Proma（github.com/proma-ai/proma，AGPL-3.0，注意不可复制代码）
- 定位：本地优先的通用 Agent 工作台（Chat + Agent + Skills + MCP + Memory + 远程机器人）；2,148 stars，日更级活跃。
- **技术栈与 LaboFlow 高度同构：Electron 39 + React 18 + TS + Jotai + Tailwind + Radix，Bun 构建**；IPC 三层契约（shared types → main handlers → preload → renderer）。
- **引擎：Pi Agent Runtime（`@earendil-works/pi-coding-agent` + `pi-agent-core` + `pi-ai`）**，主进程 `agent-orchestrator.ts` + `adapters/pi-agent-adapter.ts` 编排；JSONL 会话持久化；渠道（channel）动态注册为 Pi provider——**LaboFlow 架构的最直接先例**。
- **Channel 模型接入抽象**（值得照抄 UX）：供应商类型（OpenAI 兼容/Anthropic/Gemini）+ BaseUrl（自动补 /v1）+ API Key（加密存储）+ "从供应商获取"拉模型列表 + "测试连接"按钮 + "Agent 供应商"标记；DeepSeek/Kimi/智谱/MiniMax/豆包/千问均兼容。
- 功能亮点：**Workspace → Project（本地文件夹）→ Session 三级模型**，每级挂 Skills/MCP/记忆/AGENTS.md；权限模式 + plan confirmation；**SubAgent（explorer/researcher/code-reviewer）+ Team 侧边栏（agent 间通信可视化）**；Skills 自然语言创建/联网发现/安装（skills-creater、find-skills）+ **组织级 Skills 分发（商业版）**；统一 MCP/CLI 连接目录 + OAuth + **图形配置与 JSON 预览双轨**；内嵌浏览器自动化；Obsidian/Office 文档预览；飞书/钉钉/微信远程派活；语音输入、Agent 状态"灵动岛"、浅/深/跟随系统主题。
- 商业模式（验证 LaboFlow 商业设想）：AGPL 开源桌面端 + 商业云（内置模型渠道低价、托管 agent 链路、**独立配额 API key、团队配额管理、组织 Skills 分发**）。
- 存储：刻意的 local-first JSON/JSONL（无数据库）——与 FreeBuddy 的 SQLite 形成对照；LaboFlow 需用量统计+配额，**建议 SQLite**。

### 4.3 腾讯 WorkBuddy（workbuddy.ai / codebuddy.cn/work）
- 定位：办公场景 agentic 工作台（"100+ AI specialists"），从自然语言指令到可验证交付物（报告/slides/表格/落地页）；Team $40/seat/月含共享 credit 池，TokenPlan BYOM（Hunyuan/DeepSeek/GLM/Kimi）。
- 值得借鉴：**单一 admin console（成员/权限/预算/共享资产）+ productivity dashboard（任务量/活跃度/配额告警）+ 定时自动化经 IM 回传 + 本地桌面执行处理本机文件**；预算上限与接近配额告警。
- 要避免："100+ experts" 式横向铺量易浅薄化；无法审计的"节省时间"类 ROI 指标。

## 五、结论一：设想功能可行性评估

**总体结论：全部核心功能技术上可行，且每个功能都有至少一个成熟先例。** 需要自建（Pi 刻意不提供）的部分：权限审批、MCP 集成、子Agent/团队编排、定时任务、服务端全部。

| # | 需求 | 可行性 | 实现路径 | 先例 |
|---|---|---|---|---|
| 1 | Pi 为核心引擎 | ✅ 已验证 | Electron 主进程内嵌 Pi SDK；锁版本+防腐层 | Proma、OpenClaw |
| 2 | 中英双语 + 亮/暗/自动主题 | ✅ 简单 | i18next + CSS variables + prefers-color-scheme | FreeBuddy/Proma |
| 3 | Electron 三平台（win-x64/mac-arm/linux-x64） | ✅ | electron-builder：exe/dmg/deb/AppImage + 自动更新 | FreeBuddy 分发矩阵 |
| 4 | Skills | ✅ 原生 | Pi 完整实现 SKILL.md 开放标准，直接复用 Claude 生态技能 | Pi 原生 |
| 5 | MCP | ⚠️ 需自建 | 基于 `@modelcontextprotocol/sdk` 写 Pi extension 适配层（参考 pi-mcp-adapter） | FreeBuddy、pi-mcp-adapter |
| 6 | 插件市场（兼容 Claude 市场+手动添加） | ✅ 格式兼容 | 解析 Claude marketplace 清单；v1 装 skills/MCP/commands，v2 兼容 hooks/agents | ZCode、Codex |

| 10 | 子Agent + Agent 团队（Agent.md/Soul.md） | ✅ 需自建 | Pi SDK spawn 子 agent（官方用例）；专家=系统提示词+工具白名单+模型/thinking 配置的具名预设 | Proma SubAgent/Team、FreeBuddy Teams |

| 16 | 登录 + 组织下发（角色/共享区/模型配置） | ✅ 需自建 | JWT + REST；模型配置下发=网关地址+虚拟 key（免配置） | WorkBuddy、Proma 商业版 |
| 17 | 初次登录强制改密 | ✅ 简单 | 服务端 must_change_password 标志 | — |
| 18 | 团队工作区（仅查看/可参与） | ✅ 需设计 | 会话同步服务端 + 权限模型；"可参与"建议串行/回合制（待头脑风暴敲定） | （无完全相同先例，最接近：WorkBuddy 共享资产） |

**三大风险**（均在可控范围，但要写进 PRD 的风险章节）：
1. Pi 上游周更 + breaking changes + 治理变动 → 版本锁定、防腐层（LaboFlow 不直接裸调 Pi API，隔一层 Core 接口）、fork 预案。
2. MCP/权限/编排全部自建 → 工作量集中在 LaboFlow Core 服务层（这层正是产品护城河）。
3. Proma 是 AGPL → 只借鉴模式，不复制代码；FreeBuddy MIT 但 license 文件缺失需二次确认后方可复用代码。

## 六、结论二：功能增补与修改建议

### 6.1 建议补充（按优先级）
1. **咨询行业 Skill 包**（差异化护城河）：MECE 议题树、金字塔原理写作、假设驱动分析、专家访谈纪要、数据清洗与分析、slide 打磨；直接复用 Claude 生态 document-skills（pptx/xlsx/docx/pdf）——Codex 官方技能库已含 PDF/表格/docx 创建，证明咨询交付物技能现成可用。
2. **交付物审阅队列**（Codex Automations review queue 模式）：定时任务/子Agent 产出的报告/PPT 统一进入队列集中审阅——对咨询非代码交付物同样成立。
3. **组织级 Skill/提示词库分发**：团队管理员沉淀方法论到共享库，一键下发给全员（Proma 商业版验证了该需求）。
4. **管理员用量看板**：任务量、活跃成员、tokens 成本、配额余量与接近配额告警（WorkBuddy 模式）。
5. **安全基线**：API key 加密存储（safeStorage/Keychain/DPAPI）、项目信任机制（打开新文件夹时的信任确认，Pi 已有 trust 概念）、审计日志（谁在何时用哪个模型消耗了多少）。
6. **自动更新 + 崩溃/错误上报**（2B 产品的运维底线）。
7. （二期）**IM 桥接**：飞书/企业微信远程派活、定时任务结果回传 IM——咨询顾问"人在客户现场、Agent 在公司跑"场景契合（Proma/WorkBuddy 均验证）。

### 6.2 建议修改/澄清
1. **定时任务执行位置**：v1 客户端调度（App 在线时执行，ZCode 模式）；服务端无人值守执行（需项目文件在服务端可及）列为 v2——避免一期就做文件同步。
2. **"可参与"权限的并发模型**：实时协同编辑同一会话复杂度过高；建议 v1 为"串行参与"（一人发言时其他人只读，或回合制）+ 会话 fork 供并行分支。待头脑风暴敲定。
3. **权限模式 + 组织策略下限**：四模式保留，但组织管理员可对指定项目/工作区强制"最严格档下限"（客户敏感数据场景刚需，借鉴 Codex granular policy + auto-review 思想）。
4. **插件市场兼容范围分期**：v1 = skills + MCP + slash commands（覆盖 superpowers、PPT-Master 类插件主体）；v2 = hooks + agents 格式兼容。
5. **网关协议**：同时讲 OpenAI Chat Completions 与 Anthropic Messages 两种协议（Pi 四种 API 类型中选这两种即可覆盖全部主流模型，含 DeepSeek/GLM/Kimi/Qwen）。
6. **本地优先原则**：未登录时客户端全功能可用（用户已明确）；登录仅叠加组织能力——这决定了客户端架构是"本地优先+增量同步"而非"在线优先"。
7. **技能/命令长期并存**：吸取 Codex 强制合并 slash commands 入 skills 引发社区反弹的教训。

## 七、结论三：UI/UX 设计规范建议

### 7.1 布局范式（五款对标产品的共识）
- **三栏布局（均可折叠）**：左侧导航（项目/会话列表，底部：用量入口、设置、账号）；中间对话/任务流（主区）；右侧上下文面板（文件树/计划/子Agent 状态/交付物，可收窄）。
- 会话视图核心元素：权限模式选择器、模型选择器、思考等级、附件、@文件引用、计划审批卡、内联工具调用卡片（diff/命令输出折叠展示）、todo 进度条。
- **状态可见性第一原则**：agent 正在做什么、等什么审批、花了多少 token，任何时刻一眼可见（ZCode 的 todo/计划门、Proma 的"灵动岛"、FreeBuddy 的用量卡片、Codex 的 threads-by-project 均为此设计）。
- Agent 团队页：团队成员卡片（角色头像/状态/当前任务）、成员间通信流可视化（Proma Team 侧边栏模式）、任务分派与回收。
- 设置页关键子页：模型渠道（Provider 预设卡片——只填 key；自定义渠道——类型/BaseUrl/测试连接/拉取模型，Proma Channel UX）、权限、自动化（定时任务列表）、Browser/Computer Use 授权页（macOS 显示 TCC 授权引导，Windows 显示范围确认）、插件市场管理。
- Web 管理台（服务端）：用户/团队/渠道/配额/审计五模块（WorkBuddy admin console 模式）。

### 7.2 视觉语言
- **明快、专业、低饱和**（咨询行业审美）：中性灰基底（参考 #f8fafc 浅 / #0b0f19 深）+ 单一品牌强调色（建议低饱和蓝或青绿系，避免花哨渐变）；语义色仅用于状态（danger/warning/success）。
- 亮/暗/跟随系统三模式；中英双语（i18next，日期/数字本地化）。
- 字体：UI 用 Inter + 思源黑体/HarmonyOS Sans SC 回退栈，代码/输出 JetBrains Mono 或系统等宽。
- 组件规范：卡片式、圆角 8-12px、细描边 + 软阴影分层；间距 4/8/12/16/24 体系；密度适中偏紧凑（工作台工具，非内容消费产品）。
- 兼容 Claude 生态技能的渲染：Markdown + Mermaid + KaTeX + 代码高亮（Shiki）+ 表格/图片/补丁 diff 渲染器。

### 7.3 交互范式
- 权限审批用内联卡片不打断心流；计划门（先批准计划再执行）；结构化提问组件（选项式而非纯文本提问）。
- Onboarding：零登录可用 → 首次启动仅两步（选主题/语言 + 配一个模型渠道）；登录页支持组织地址；渠道配置带"测试连接"即时反馈。
- 反模式（对标教训）：不做多入口产品碎片化（一个桌面端+一个 Web 管理台，身份清晰）；不做"百人专家市场"式铺量；不强制迁移砍旧功能。

## 八、结论四：产品架构规划建议

### 8.1 总体架构（"one kernel, multiple shells"）
```
┌─ LaboFlow 客户端（Electron，win-x64 / mac-arm / linux-x64）────────────┐
│ 渲染进程（React UI：项目/会话/团队/市场/设置）                          │
│   ↕ IPC（shared types 三层契约）                                       │
│ 主进程 = LaboFlow Core（自建，产品护城河层）                            │
│   • AgentService：内嵌 Pi SDK（锁版本），会话/steer/compaction          │
│   • PermissionEngine：tool_call 钩子 → 四模式审批 + 组织策略下限        │
│   • McpBridge：MCP SDK ↔ Pi extension 适配                             │
│   • Orchestrator：子Agent/专家团队（Agent.md+Soul.md 具名预设）         │
│   • Scheduler：定时任务（持久化，ZCode Cron 语义）                      │
│   • UsageRecorder：token/成本记账 → SQLite                             │
│   • Marketplace：Claude 插件市场格式解析 + 手动市场源                   │
│   • BrowserUse（内嵌 Chromium/CDP）/ ComputerUse（AX/UIA+TCC）         │
│   • SyncClient：登录后与组织服务器同步（本地优先，增量）                 │
│   • 存储：better-sqlite3（会话索引/用量/配置/任务）                      │
└──────────────────────────────────────────────────────────────────┘
          ↕ HTTPS（REST + WS 推送；未登录时完全离线可用）
┌─ LaboFlow 服务端（Docker，Linux-x64）──────────────────────────────┐
│ • API 网关：认证（JWT/初次改密）、RBAC（系统管理员/团队管理员/用户）   │
│ • 模型中转网关：OpenAI+Anthropic 双协议代理、计量、配额引擎            │
│   （会话数/Tokens × 日/周/月；系统级 > 团队级，从严者生效）            │
│ • 共享工作区服务：团队会话存储（仅查看/可参与）、共享文件、组织 Skill 库 │
│ • 配置下发：角色、模型配置（网关地址+虚拟 key）                        │
│ • Postgres（+可选 Redis）；审计日志                                    │
│ • Web 管理控制台（React）                                              │
│ • Caddy/Traefik + acme.sh：SSL 自动申请/部署/续期                      │
└──────────────────────────────────────────────────────────────────┘
```

### 8.2 关键技术决策建议
1. **客户端栈**：Electron + React + TypeScript；状态 Zustand 或 Jotai；UI 用 antd（FreeBuddy 路线，管理密集型界面效率高）或 Tailwind+Radix（Proma 路线，视觉自由度高）——待头脑风暴敲定；i18next 双语；better-sqlite3。
2. **Pi 防腐层**：所有 Pi 调用收口到 LaboFlow Core 的内部接口（AgentService），UI 永不直触 Pi；Pi 升级只改 Core 一处。
3. **本地优先数据流**：本地 SQLite 为客户端权威；登录后共享区会话以服务端为权威、客户端缓存；离线可用，在线增强。
4. **服务端栈**：NestJS（TypeScript，与客户端同语言降维护成本）或 Go（网关性能）；Postgres；docker compose 一键部署；网关自研双协议代理（参考 one-api 模式）。
5. **安全**：客户端 key 用 OS keychain（safeStorage）；服务端虚拟 key（用户永远拿不到组织的真实上游 key）；项目信任确认；审计日志。

### 8.3 子项目分解（建议的开发顺序，待讨论）
1. **P1 客户端本地 Harness MVP**：Pi 内嵌 + 项目/会话 + 权限四模式 + Skills/MCP + BYOM 渠道 + 用量统计 + 基础定时任务。→ 单机即完整可用，可先交付顾问个人使用。
2. **P2 服务端 + 组织协作**：认证/RBAC/团队 + 模型网关与配额 + 共享工作区 + 配置下发 + SSL + Web 管理台。
3. **P3 增强**：Agent 团队深化、插件市场完整兼容（hooks/agents）、Browser/Computer Use、审阅队列、IM 桥接。

> 理由：引擎体验是产品根基（Proma/FreeBuddy 均以单机版验证需求起步）；服务端围绕已验证的客户端形态设计更准；P3 依赖 P1/P2 的用户反馈。
